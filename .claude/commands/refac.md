# /refac — рефакторинг ArcanaGlyph по бэклогу аудита

Ведёт рефакторинг репозитория по файлу-бэклогу с чекбоксами в `docs/refactoring/`.
Источник пунктов — прогон `/aidit`. Это **исполнение** (правки кода по плану), а НЕ
диагностика — полный аудит без правок живёт в `/aidit`.

## 🛑 ГЛАВНОЕ ПРАВИЛО — НИКОГДА НЕ ПУШИТЬ (прямая воля пользователя)

**`git push` / `git push -u` / merge в удалённую — ЗАПРЕЩЕНЫ в этой команде во всех
режимах, включая `auto`.** Это переопределяет любые «auto»-гранты. Что можно и что нельзя:

- ✅ **Коммитить можно** — после каждого закрытого пункта или после шага рефакторинга
  (пользователь это разрешил специально для `/refac`). `git add <конкретные файлы>`
  (НЕ `-A`) → `git commit`. Сообщения — на английском, без версии, без Co-Authored-By.
- ❌ **Пушить нельзя** — ни автоматически, ни «за компанию», ни по завершении файла.
- 📦 **Финал — squash + push делает ТОЛЬКО пользователь вручную.** Набравшиеся за прогон
  коммиты потом объединяются в один и пушатся руками пользователя. Максимум от меня —
  показать команды squash по запросу.

Если возникает соблазн запушить «чтобы не потерять» — СТОП: коммит уже сохраняет работу
локально, push не нужен. Ветка `dev` делегирована для коммитов, но push — всегда пользователь.

## Директория рефакторинга и зеркало

- `docs/refactoring/` **коммитится в наш репозиторий** — это история «что рефакторили и
  почему» (бэклог + отметки + commit-хэши). НЕ добавлять в `.gitignore`.
- Но она **вырезается из публичного GitHub-зеркала** (`git rm -rf docs/refactoring/` в job
  `mirror-to-github` `.gitlab-ci.yml`) — внешним не нужно видеть нашу внутреннюю кухню.
- Бэклог-файл и правки кода одного пункта коммить вместе (одним коммитом) — так история
  самодокументируется.

## Аргумент (`$ARGUMENTS`)

- пусто — **интерактивный** режим (один пункт, затем стоп).
- `auto` — **автономный** режим (см. §4). Push всё равно запрещён.
- `rescan` — принудительно перегнать `/aidit` и дописать новые находки в активный файл
  (не трогая отметки), затем продолжить.

## 0. Старт

- `mcp__arcana-codex__ping` — первое действие, без исключений.
- **Self-heal архивации** (идемпотентно, §3): просканировать `docs/refactoring/*.md` — если
  какой-то файл полностью закрыт, но ещё не в `archive/`, доархивировать сейчас.
- Найти в `docs/refactoring/` **активный** (не в `archive/`) файл-бэклог с неотмеченными
  пунктами (`[ ]`).

## 1. Развилка: активный файл / всё в архиве / ничего нет

Три случая — **новый аудит НЕ запускается автоматически, если долг уже закрыт**:

- **Активный файл есть** (неархивный, с пунктами `[ ]`) → НЕ запускать аудит (экономим
  прогон, не плодим дубли). К §2.
- **Активного файла нет, но в `archive/` уже есть закрытые бэклоги** (весь прошлый долг
  закрыт) → 🛑 **НЕ запускать новый аудит молча.** Спросить (`AskUserQuestion`,
  recommended-первым): «Весь рефакторинг-долг закрыт. Что дальше?» →
  - «Провести новый аудит» → прогнать `/aidit`, создать новый файл-бэклог (см. ниже), спросить старт.
  - «Завершить» → доложить «рефакторинг-долга нет» и остановиться.
- **Активного файла нет И `archive/` пуст** (самый первый запуск) → запустить полный аудит
  (логика `/aidit`), создать `docs/refactoring/<YYYY-MM-DD>-audit-backlog.md`: находки
  сгруппированы по темам, чекбоксы `[ ]`, пометки 🔒 (footgun-gated) / ⚠️ (крупная правка),
  в шапке — регламент (этот протокол + «не пушить»). После создания — **спросить**
  (`AskUserQuestion`): начать рефакторинг сейчас или остановиться.

> Итог: молчаливый полный аудит бывает **только при самом первом запуске** (архива ещё нет).
> Когда всё в архиве — команда всегда спрашивает, а не жжёт прогон сама.

## 2. Один пункт за итерацию

Берём **первый** неотмеченный `[ ]` пункт по порядку.

1. **Verify-before-refactor.** Перепроверить, что находка ещё актуальна — повторно вызвать
   соответствующий MCP-тул на цель. Код мог измениться: находка могла стать false-positive
   или закрыться побочно. Если неактуальна → отметить `[~]` с пометкой «устарело/FP», при
   необходимости defer-sync (§5), к следующему пункту.
2. 🔒 **Footgun-gated.** Если на файл есть advisory-плагин — вызвать `applicable_rules(<файл>)`
   и прочитать напоминание ПЕРЕД правкой (whisper abort-callback UB, платформо-вставка
   input.rs, tauri dead-code, changelog version-bump). Не нарушать инвариант плагина.
3. **Режим планирования.** `EnterPlanMode` → составить план правки → согласовать через
   `ExitPlanMode`. Без утверждённого плана не править.
4. **Правка** — behaviour-preserving, минимальная под пункт. Для переименований —
   `rename_symbol`; для извлечения модуля — по `extract_module_suggestion`.
5. **Dogfood-ритуал (полный, 6 шагов из `CLAUDE.md` — не урезать):** `cargo fmt --all` →
   `cargo clippy --workspace --all-targets -- -D warnings` → MCP coverage-check
   (`untested_publics` на изменённый модуль — новый pub без теста дописать СЕЙЧАС) →
   MCP refactor-check (`file_health` + `refactor_candidates(scope="staged")`) → если flagged
   actionable → дочистить сейчас → `cargo fmt --all -- --check` + `cargo test --workspace`.
   Фронтенд (`frontend/`): `npm --prefix frontend run type-check` (+ vitest если затронут).
6. **Поведение не поехало** (рефактор ≠ фича): `semantic_diff` / `breaking_changes` на
   тронутых публичных символах — сигнатуры/контракты не должны измениться молча.
7. **Отметка + коммит.** В файле: `[ ]` → `[x]`, в колонку «Готово» — commit-хэш. Коммит
   (бэклог + код вместе, конкретные файлы, английский, без версии). **НЕ пушить** (§ГЛАВНОЕ).

## 3. Завершение пункта и архивация бэклога

- После отметки пункта: в интерактивном режиме — **стоп**, короткий отчёт (что сделано,
  что NEXT), ждать нового `/refac`. В `auto` — к следующему пункту.

**Архивация закрытого бэклога — обязательна и идемпотентна:**

- **Цикл закрыт** = в файле не осталось `[ ]` (все пункты `[x]` сделаны или `[~]` FP/wontfix).
- **Self-heal на КАЖДОМ запуске (в §0):** просканировать `docs/refactoring/*.md` (верхний
  уровень, НЕ `archive/`). Любой файл, где все чекбоксы закрыты, но он ещё не в `archive/` —
  доархивировать. Идемпотентно: уже архивированные не трогать (так закрытие не потеряется,
  даже если прошлая сессия оборвалась до архивации).
- **Процедура:**
  1. Во front-matter файла: `status: closed` + `closed: <дата>`; убедиться, что все пункты закрыты.
  2. `git mv docs/refactoring/<file>.md docs/refactoring/archive/<file>.md` (сохранить историю;
     поправить относительные ссылки — они стали на уровень глубже).
  3. Закоммитить архивацию (отдельным коммитом или вместе с последним пунктом). **Push — НЕТ.**
- После архивации — доложить и напомнить: финальный squash + push пользователь делает сам.

## 4. Автономный режим `/refac auto`

Грант автономии на сессию (кроме push — он ЗАПРЕЩЁН, см. §ГЛАВНОЕ):

- **Решаешь технические развилки сам как эксперт по проекту** — НЕ спрашивать
  `AskUserQuestion` по тому, что в состоянии решить сам (FP vs реальная находка, объём
  правки, каким seam'ом резать, формулировка defer-reason). Фиксируешь обоснование в
  чекбоксе/отчёте и идёшь дальше. Молчаливый вопрос «правильно ли понял пункт?» — анти-паттерн.
- **Доделывать ДО КОНЦА с первого раза** — полный dogfood-ритуал (§2 шаг 5), без «потом
  дочищу». Один пункт целиком > три наполовину.
- **Коммит после каждого пункта — можно** (конкретные файлы, не `-A`). Память (если
  правилась) — отдельным `chore(memory):` коммитом. **Push — НЕТ, никогда.**
- **Deploy/live-verify** после содержательной правки — `make run` могу сам; `make install`
  и sudo — руками пользователя ([[install-workflow]]), не запускаю. Предложить пользователю.
- **Берёшь пункты сам, последовательно** — выполнил, закоммитил, отметил → следующий.
  Без вопросов «продолжать?».
- **Частичный FP — это РАБОТА, не СТОП.** Реальную часть реализовать полностью, FP-часть
  задокументировать в чекбоксе (`[x]` + «verify-FP: <обоснование>») + defer-sync (§5).
- **СТОП-условия — только три, узкие (спросить пользователя):**
  - пункт 🔒 footgun-gated (плагин-инвариант) или ⚠️ BIG — подтверждение перед сносом большого;
  - пункт требует продуктового / библиотечного / breaking решения (выбор crate, смена API,
    внешний контракт) — ждёт слова пользователя;
  - находка при verify оказалась целиком спорной гипотезой, которую нельзя подтвердить ни
    тулом, ни чтением кода (не путать с честным FP-выводом, где агент УВЕРЕН → там `[x]`/`[~]`).
- **Свежесть контекста.** После каждого закрытого пункта — оценить остаток. Близко к
  переполнению ИЛИ следующий пункт крупный → **честный СТОП + просьба перезапустить сессию**
  и дать `/refac auto` заново. 🛑 НИКОГДА не запускать `ScheduleWakeup` / `/loop` самовольно.
- Когда все чекбоксы закрыты — архивировать файл (§3), доложить. Push не делать.

## 5. Синхронизация defer-list (`.arcanacodex.toml`)

Если пункт признан **by-design / не рефакторить** (`[~]` wontfix):

- Добавить запись `[[audit.defer]]` в `.arcanacodex.toml` (`file`/`glob` + содержательный
  `reason`) — чтобы следующий `/aidit` её не поднимал. Свериться, нет ли уже такой (не дублировать).

## Напоминание в конце каждого прогона

- Что сделано (пункты + commit-хэши), что осталось `[ ]`.
- **«Закоммичено локально, НЕ запушено. Финальный squash + push — за тобой.»**
- Если нужно — по запросу показать команды squash набравшихся коммитов (не выполнять push сам).
